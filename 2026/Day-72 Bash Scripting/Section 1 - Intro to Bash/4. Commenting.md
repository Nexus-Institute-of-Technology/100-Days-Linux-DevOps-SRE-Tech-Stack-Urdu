# 📖 Introduction

Comments are an important part of Bash scripting.

They help make scripts easier to:

- Read
- Understand
- Maintain
- Troubleshoot
- Share with other administrators

A comment explains what a section of code is doing.

Comments are especially useful when:

- A command is not self-explanatory.
- A script contains complex logic.
- A function performs a specific task.
- Another administrator may need to understand the script later.
- You return to your own script after several months.

The Bash interpreter ignores comments during execution.

---

# What Is a Comment?

A **comment** is text written inside a script for documentation.

It is not treated as an executable command.

A Bash comment normally begins with:

```text
#
```

Anything written after the hash character on that line is ignored by Bash.

Example:

```bash
# This is a comment
```

---

# Basic Comment Syntax

```bash
# Your comment goes here
```

Example:

```bash
# Display a greeting message
echo "Hello Friend"
```

When the script runs, Bash executes:

```bash
echo "Hello Friend"
```

but ignores:

```bash
# Display a greeting message
```

---

# Why Are Comments Important?

Comments improve:

- Code readability
- Script documentation
- Troubleshooting
- Team collaboration
- Long-term maintenance

A well-commented script allows another administrator to quickly understand:

- What the script does.
- Why certain commands are used.
- What each section is responsible for.
- What variables or functions represent.

---

# The Shebang Is Not a Comment

The first line of a Bash script usually contains:

```bash
#!/bin/bash
```

Although it begins with the hash character (`#`), it is **not a normal comment**.

It is the **Shebang line**.

The Shebang tells Linux which interpreter should execute the script.

Example:

```bash
#!/bin/bash
```

This means:

> Use `/bin/bash` to interpret this script.

---

# Comment vs Shebang

| Line | Purpose |
|------|---------|
| `#!/bin/bash` | Selects the Bash interpreter |
| `# This is a comment` | Documentation ignored by Bash |

The Shebang should remain the first line of the script.

Any other line beginning with `#` is normally treated as a comment.

# Script Execution Flow

```text
#!/bin/bash
      │
      ▼
Select Bash Interpreter
      │
      ▼
# Comment
      │
      └── Ignored
      │
      ▼
echo "Hello Friend"
      │
      └── Executed
      │
      ▼
# Comment
      │
      └── Ignored
      │
      ▼
date
      │
      └── Executed
```

---

# Full-Line Comments

A full-line comment begins with `#`.

Example:

```bash
# Create a backup directory
mkdir -p /backup
```

The first line documents the purpose of the command below it.

---

# Inline Comments

A comment may also appear after a command.

Example:

```bash
echo "Hello Friend"  # Print a greeting
```

Bash executes the command before the hash and ignores the comment after it.

---

# Inline Comment Example

```bash
date  # Display the current date and time
```

The command runs normally.

The text after `#` is ignored.

---

# Important Spacing Note

This is a normal comment:

```bash
echo "Hello Friend"  # Print a greeting
```

It is good practice to include spaces before the inline comment.

This improves readability.

---

# Comments Inside Quotation Marks

A hash character inside quotation marks is treated as normal text.

Example:

```bash
echo "This # symbol is part of the message"
```

Output:

```text
This # symbol is part of the message
```

The hash is not treated as a comment because it is inside quotes.

---

# Quoted vs Unquoted Hash

```bash
echo "Hello # Friend"
```

Output:

```text
Hello # Friend
```

But:

```bash
echo Hello # Friend
```

Output:

```text
Hello
```

In the second example, Bash treats:

```text
# Friend
```

as a comment.

---

# Commenting Out a Command

Comments can temporarily disable a command.

Suppose the script contains:

```bash
echo "Hello Friend"
date
```

To prevent the `date` command from running:

```bash
echo "Hello Friend"

# date
```

The command remains in the file but is ignored.

This is useful during testing and troubleshooting.

---

# Example: Temporarily Disable a Command

```bash
#!/bin/bash

echo "Starting script"

# rm -rf /tmp/test-data

echo "Script completed"
```

The `rm` command does not run because it is commented out.

---

# Using Comments as Section Headings

Comments can separate a long script into logical sections.

Example:

```bash
#!/bin/bash

# ==========================
# Configuration
# ==========================

BACKUP_DIR="/backup"

# ==========================
# Create Backup Directory
# ==========================

mkdir -p "$BACKUP_DIR"

# ==========================
# Display Completion Message
# ==========================

echo "Backup directory created"
```

This makes long scripts easier to navigate.

---

# Good Commenting Practices

Good comments should explain:

- Why something is being done.
- What a complex command accomplishes.
- What a variable represents.
- What a function is responsible for.
- Important assumptions or warnings.

---

# Good Comment Example

```bash
# Keep only the last seven backup files to save disk space.
ls -1t /backup/*.tar.gz | tail -n +8 | xargs -r rm --
```

The comment explains the purpose of the command.

---

# Avoid Obvious Comments

Poor comment:

```bash
# Run the date command
date
```

This is not harmful, but the command is already self-explanatory.

A more useful comment might be:

```bash
# Record the script execution time in the backup log.
date >> /var/log/backup.log
```

The comment explains **why** the command is being used.

---

# Comments and Functions

Comments become especially useful when scripts contain functions.

Example:

```bash
#!/bin/bash

# Create a compressed archive of the application configuration.
create_backup() {
    tar -czf /backup/app-config.tar.gz /etc/myapp
}

create_backup
```

The comment explains the purpose of the function.

---

# Comments and Variables

Example:

```bash
# Directory where completed backups are stored.
BACKUP_DIR="/backup"
```

This helps readers understand the variable immediately.

# 🔧 Troubleshooting

## Problem 1 – Comment Appears in the Output

Check whether the hash is inside quotation marks.

Example:

```bash
echo "# This text will be printed"
```

Because the hash is inside quotes, Bash treats it as text.

---

## Problem 2 – Command Does Not Run

Check whether the line begins with:

```text
#
```

Example:

```bash
# date
```

The command is commented out.

Remove the hash:

```bash
date
```

---

## Problem 3 – Shebang Was Commented Out

Do not add another character before the Shebang.

Correct:

```bash
#!/bin/bash
```

Incorrect:

```bash
# #!/bin/bash
```

The correct Shebang must start at the beginning of the first line.

---

## Problem 4 – Inline Comment Breaks the Command

Make sure the hash is placed after the complete command.

Correct:

```bash
echo "Hello Friend"  # Greeting
```

Incorrect:

```bash
echo # "Hello Friend"
```

The incorrect example executes only:

```bash
echo
```

because everything after the hash is ignored.

---

# 📌 Quick Revision

| Syntax | Purpose |
|--------|---------|
| `# Comment` | Add a full-line comment |
| `command # Comment` | Add an inline comment |
| `#!/bin/bash` | Select the Bash interpreter |
| `# command` | Temporarily disable a command |
| `echo "# text"` | Print a hash as normal text |

---

# 📖 Key Takeaways

- Bash comments normally begin with `#`.
- Comments are ignored during script execution.
- Comments improve readability and documentation.
- The Shebang begins with `#`, but it is not a normal comment.
- Comments can be written on separate lines or after commands.
- A hash inside quotation marks is treated as normal text.
- Comments can temporarily disable commands during testing.
- Professional scripts should include meaningful documentation.

---

# 💡 Remember

> **Think of comments as notes written in the margin of a textbook.**
>
> - The reader can see and understand the notes.
> - The notes explain the material.
> - The notes do not become part of the actual lesson execution.
> - Bash reads the commands but skips the comments.
>
> **Golden Rule:**
>
> ```text
> # Comment
>      │
>      ▼
> Ignored by Bash
>
> Command
>      │
>      ▼
> Executed by Bash
> ```
>
> Use comments to explain **why** your script performs an action, not only to repeat what the command already says.
